\subsection*{(b) Dominant CUDA kernel and invocation count}
In the forward pass, the highest cumulative-GPU-time kernel is generally a GEMM kernel (for example, \texttt{ampere\_sgemm\_128x64\_tn} for small/medium/large at context length 128). For small@128 forward, this top kernel was invoked 25 times in one forward pass. The dominant kernel is not always the same once backward is included (e.g., small@128 train-step is dominated by a different GEMM variant), so the answer is configuration-dependent.

Here, a kernel name like ``ampere sgemm 128x64 tn'' denotes an Ampere-optimized single-precision matrix-multiplication kernel. The 128x64 part indicates tile shape, and tn indicates transpose/non-transpose layout choices for GEMM operands.

\subsection*{(c) Non-matmul kernels with non-trivial runtime}
Beyond GEMMs, non-trivial forward runtime comes from elementwise and reduction kernels, including direct copy/masked fill/indexing and reduction-style kernels used by normalization and softmax-related computation. These appear consistently in the top non-GEMM entries across model sizes.

\subsection*{(d) Training-step vs inference kernel mix}
On configurations where both modes fit in memory, matrix-multiplication kernels account for about 80.0\% of CUDA kernel time in forward-only runs versus about 71.4\% in full training steps. So compared to inference, training shifts more time into non-matmul work (backward elementwise/reduction kernels and optimizer multi-tensor update kernels).

\subsection*{(e) Softmax vs matmul within self-attention}
Using an additional attention-annotated forward profile (medium@128), the summed attention softmax runtime was 48.61 ms, while attention matrix multiplications were 30.31 ms (QK) + 21.94 ms (PV) = 52.25 ms. This runtime gap is much smaller than the FLOP gap (matmuls are far higher FLOPs), consistent with softmax and related steps being more memory-bound and less compute-efficient than GEMMs.

\subsection*{(b) Why this happens}
Accumulating directly in FP16 is much less accurate because FP16 has far fewer mantissa bits, so repeated additions incur larger rounding error. Using an FP32 accumulator significantly improves stability, but if each addend is first quantized to FP16 then that quantization error is still present, which is why cases (3) and (4) match each other and remain less accurate than pure FP32 accumulation.

\section{Problem: benchmarking\_mixed\_precision}
\subsection*{(a) Dtypes under FP16 autocast}
Assuming model parameters are initialized in FP32 and training is done on CUDA with FP16 autocast (for example, \texttt{torch.autocast(...)} configured with \texttt{dtype=torch.float16}):
\begin{itemize}
\item Model parameters inside autocast: FP32 (autocast does not permanently cast parameters).
\item Output of \texttt{ToyModel.fc1}: typically FP16.
\item Output of \texttt{ToyModel.ln}: typically FP32 (layer norm is on autocast's FP32-safe path).
\item Model logits (\texttt{ToyModel.fc2} output): typically FP16.
\item Loss: typically FP32 for common PyTorch loss ops under autocast.
\item Gradients: FP32 (matching FP32 parameter storage dtype).
\end{itemize}

\subsection*{(b) Why layer norm is treated differently}
Layer norm computes per-feature statistics (mean/variance) and involves reductions plus subtract/square/rsqrt operations that are numerically sensitive to precision. FP16 can lose significant accuracy (and may overflow/underflow more easily), so running layer norm in FP32 is safer. BF16 has a wider exponent range than FP16 (so overflow is less problematic), but it still has limited mantissa precision, so FP32 treatment of normalization remains helpful for stability.

\subsection*{(d) Residual-stream activation size}
For one residual-stream activation tensor in FP32, size is
\[
= \mathrm{batch} \times \mathrm{context} \times d_{\mathrm{model}} \times 4\ \mathrm{bytes}
\]
\[
= 4 \times L \times 2560 \times 4.
\]
So this is \(40960L\) bytes, i.e. \(5\) MB at \(L{=}128\), \(10\) MB at \(L{=}256\), and \(20\) MB at \(L{=}512\) (using MB \(=1024^2\) bytes).

\subsection*{(e) Largest allocations at reduced detail}
Inspecting the saved snapshot data for forward runs shows largest active allocations in large chunks (e.g., up to \(\sim\)100 MB blocks in the allocator snapshot, with frequent 40 MB blocks). The available stack traces in this environment resolve mainly to the CUDA caching allocator internals, so the coarse interpretation is that these largest blocks correspond to persistent model/activation storage managed by the allocator during large forward GEMM-heavy regions.

\subsection*{Memory accounting and scaling}
Using the smallest failing setting (\(B{=}8\), \(L{=}16384\), \(d_{\text{model}}{=}16\), FP32), one \(B \times L \times L\) tensor requires:
\[
8 \times 16384 \times 16384 \times 4 = 8{,}589{,}934{,}592\ \text{bytes} \approx 8\ \text{GiB}.
\]
Naive attention materializes large \(L \times L\) intermediates (scores/probabilities), and backward needs saved activations plus additional gradient/intermediate buffers, so memory pressure rises quickly. Since these dominant tensors scale as \(O(BL^2)\), saved-for-backward memory grows quadratically with sequence length: doubling \(L\) increases this memory by about \(4\times\). This matches the measured trend from about 1.0--1.1 GiB at \(L{=}4096\) to about 4.0--4.3 GiB at \(L{=}8192\).

To eliminate this \(L^2\) memory cost, avoid materializing the full attention matrix.
Use tiled attention plus recomputation checkpointing so backward does not keep full score/probability matrices in memory.
